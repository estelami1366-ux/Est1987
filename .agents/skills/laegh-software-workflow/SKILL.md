# گردش‌کار نرم‌افزار لایق الکترونیک پارسیان

این یک پروژه‌ی واقعی و در حال استفاده است (نه نمونه یا آزمایشی). صاحب کسب‌وکار از این نرم‌افزار برای کار روزمره استفاده می‌کند و از دست رفتن داده در این پروژه واقعاً قبلاً اتفاق افتاده. رعایت دقیق این قوانین اختیاری نیست.

ارتباط با کاربر همیشه به **فارسی، مستقیم و خلاصه** است — همانطور که در طول این پروژه انجام شده.

سند معماری بلندمدت: `docs/ARCHITECTURE_RULES.md` (قانون ۱۲).
حاکمیت توسعه و حفاظت کد پایدار: `docs/DEVELOPMENT_GOVERNANCE.md` (قانون ۱۳).
این اسناد باطل‌کنندهٔ قوانین ۱ تا ۱۱ نیستند.

## قانون ۱ — هرگز بدون اجرای تست خودکار، فایل تحویل نده

فایل `test_laegh.js` (در پروژه موجود است) باید قبل از هر `present_files` روی فایل HTML نهایی اجرا شود:

```bash
node test_laegh.js path/to/Laegh_Final_X.html
```

- اگر حتی یک تست ❌ شد: فایل تحویل **نمی‌شود**. اول باگ را رفع کن، دوباره تست بزن.
- مهم‌ترین تست («گروه ۰») کل اسکریپت را در یک محیط شبیه‌سازی‌شده (Node `vm` + mock DOM/localStorage) واقعاً اجرا می‌کند — نه فقط جستجوی متن. این تست انواع `ReferenceError`/`TypeError` ناشی از ترتیب نادرست تعریف متغیر را می‌گیرد (دقیقاً نوع باگی که قبلاً واقعاً رخ داد: کد بررسی نیاز به صفحه ورود، قبل از تعریف متغیر `loginPw` نوشته شده بود و این باعث قفل‌شدن دائمی نرم‌افزار شد بدون اینکه کاربر اصلاً رمزی تنظیم کرده باشد).
- هرگاه ویژگی جدیدی اضافه می‌کنی، یک گروه تست جدید هم به `test_laegh.js` اضافه کن که دقیقاً همان ویژگی را با اجرای واقعی منطق (نه فقط `indexOf` روی متن) چک کند. قبل از اینکه تست جدید را قبول کنی، با برگرداندن عمدی همان باگ روی یک کپی موقت فایل، مطمئن شو تست واقعاً قرمز می‌شود — وگرنه تست بی‌فایده است.
- اگر یک تست متنی (text-matching) به اشتباه «پاس» داد ولی واقعاً منطق اجرا نمی‌شود (مثل وقتی یک رشته در یک شرط `if(false)` غیرقابل‌اجرا قرار دارد)، تست را با یک نسخه‌ی execution-based جایگزین کن.

## قانون ۲ — قالب شماره‌نسخه: Major.Month.Day (تاریخ شمسی)

شماره نسخه **نباید** شمارش ساده‌ی بالارونده باشد (نه v11، v12، ...). فرمت صحیح:

```
{Major}.{ماه شمسی}.{روز شمسی}
```

مثال: انتشار در ۲۹ خرداد با نسخه‌ی اصلی ۱۰ → `10.3.29`

⚠️ **همیشه تاریخ شمسی واقعی همان روز را با دستور واقعی چک کن** (مثلاً `date` در bash و تبدیل به شمسی، یا کتابخانه `jdatetime` در پایتون). هرگز از یک تاریخ مثالی که قبلاً در توضیحات گفته شده کپی نکن — این دقیقاً همان اشتباهی بود که قبلاً رخ داد (نسخه به اشتباه `10.3.28` نام‌گذاری شد در حالی که تاریخ واقعی ۲۹ بود).

شماره نسخه باید در **همه‌ی این مکان‌ها** هم‌زمان و یکسان بروزرسانی شود:
1. تگ‌های `<meta name="app-version" content="...">`
2. متن پایین سایدبار (مثلاً «نسخه ۱۰.۳.۲۹ — Laegh EPS»)
3. فیلد `version` در آبجکت بک‌اپ (`exportData`)
4. نام فایل تحویلی (مثلاً `Laegh_Final_10.3.29.html`)

شماره نسخه باید **داخل خود نرم‌افزار در حال اجرا هم قابل مشاهده باشد** (نه فقط در نام فایل) — کاربر باید بتواند بدون باز کردن کد، نسخه‌ی نصب‌شده را در رابط کاربری ببیند.

⚠️ توجه: تابع `migrateBackup` نباید با `parseFloat(d.version)` نسخه را عدد کسری فرض کند، چون فرمت سه‌بخشی (`10.3.29`) با `parseFloat` ناقص پارس می‌شود (می‌شود `10.3`). اگر منطق migration به عدد نسخه برای تصمیم‌گیری نیاز داشت، باید رشته را با `.split('.')` جدا کند، نه `parseFloat`.

## قانون ۳ — محصول UI: یک فایل HTML تک‌تکه (نه چند فایل JS جدا)

رابط کاربری که دست کاربر می‌رسد باید **یک فایل HTML تنها** باشد (دوبار کلیک، یا داخل exe). این برای UI است، نه مجوزی برای ریختن منطق کسب‌وکار داخل JS:
- تقسیم UI به چند فایل JS جدا (حتی به نیت تمیزی کد) یک‌بار امتحان شد و دو بار به‌خاطر گم‌شدن متغیرهای سراسری بین توابع (مثل `pb`, `PB_CATS`) شکست خورد.
- اگر نیاز به توسعه روی فایل‌های کوچک‌تر بود، فقط با یک تقسیم **ساده و قابل اثبات با diff بایت‌به‌بایت** (نه استخراج پیچیده با regex) انجام شود، و یک اسکریپت build باید دوباره همه را به یک فایل واحد بچسباند قبل از تحویل.
- هرگز چندین فایل HTML/JS را مستقیماً به کاربر نهایی به‌جای محصول UI تحویل نده.
- هستهٔ .NET (پوسته WebView2 + Host Object) بخشی از محصول دسکتاپ است و با قانون تک‌فایلی UI در تضاد نیست. منطق کسب‌وکار جدید باید به سمت Core برود، نه اینکه HTML را به چند فایل JS بشکند.
- بازنویسی کل HTML یا عوض کردن فریم‌ورک بدون درخواست صریح کاربر ممنوع است.

## قانون ۴ — بک‌اپ و Migration

- `exportData` باید **همه‌ی** بخش‌های موجود نرم‌افزار (فاکتور، کالا، انبار، مخاطبین، قطعات، خدمات، گارانتی، فروش، تنظیمات پرینت، اطلاعات شرکت، لوگو، و — اگر سیستم دسترسی کاربران وجود دارد — `userRoles`/`loginPw`) را در فایل بک‌اپ بگذارد، وگرنه با تغییر نسخه نرم‌افزار، داده‌ها قابل بازیابی نخواهند بود.
- `importData`/`migrateBackup` باید بک‌اپ‌های قدیمی (حتی نسخه‌های خیلی قبل که فیلدهای جدید را ندارند، مثل بک‌اپ v2.0 که فقط `phonebook` با `fn/ln` دارد نه `pb` با `name/phone`) را بدون کرش بپذیرد و به فرمت فعلی تبدیل کند.
- دو حالت بازگردانی همیشه باید وجود داشته باشد: **ادغام** (رکوردهای جدید اضافه می‌شوند، چیزی پاک نمی‌شود) و **جایگزینی** (همه‌چیز با بک‌اپ عوض می‌شود).
- ⚠️ نکته‌ی حیاتی که قبلاً باعث باگ واقعی شد: مطمئن شو منطق بازگردانی، داده را در **همان متغیری که صفحه واقعاً از آن می‌خواند برای نمایش** می‌ریزد. مثلاً اگر دو متغیر `pb` و `phonebook` هر دو وجود دارند ولی فقط `renderPB()` از `phonebook` می‌خواند، پر کردن فقط `pb` باعث می‌شود بک‌اپ "موفق" به نظر برسد ولی صفحه خالی بماند. این نوع باگ را فقط با اجرای واقعی (نه خواندن متن کد) می‌توان گرفت — به قانون ۱ مراجعه کن.

## قانون ۵ — تابع ریست کامل (resetAll)

- باید **همیشه و بدون استثنا** قبل از پاک کردن داده، یک بک‌اپ کامل و اجباری بگیرد (با صدا زدن `exportData()`) — نه با تکیه به اینکه کاربر از قبل بک‌اپ گرفته باشد.
- باید تأیید نهایی را با **تایپ یک کلمه‌ی مشخص** (مثل «تایید») بگیرد، نه فقط یک کلیک ساده روی `confirm()` که به‌اشتباه راحت زده می‌شود.
- باید کلیدهای حساس (رمز مدیر، تنظیمات تم، لوگو) را در یک لیست `protectedKeys` صریح از حذف مستثنی کند.
- اگر سیستم دسترسی کاربران وجود دارد، باید متغیرهای حافظه (`userRoles=[]`, `loginPw=''`) را هم خالی کند، نه فقط کلیدهای `localStorage` روی دیسک — وگرنه نرم‌افزار بعد از ریست فکر می‌کند هنوز پروفایل و رمز دارد.

## قانون ۷ — هر بخش جدید، راهنمای خودش را هم داشته باشد

هرگاه یک صفحه، ماژول، یا ویژگی جدید به نرم‌افزار اضافه می‌شود (مثلاً فروش چندقلمی، ماژول حسابداری، تقویم، وظایف، و...)، **حتماً** راهنمای استفاده از آن هم به صفحه‌ی راهنما (`page-help`) اضافه شود. راهنما باید:

- درخت راهنما (help-tree) شامل گره‌ی جدید با عنوان واضح باشد.
- توضیح دهد که بخش جدید چه کاری انجام می‌دهد و چطور باید از آن استفاده کرد.
- اگر بخش جدید فرم، دکمه، یا فیلد خاصی دارد، کاربرد هرکدام را توضیح دهد.
- اگر نیاز به پیش‌نیاز دارد (مثلاً «ابتدا باید حساب تعریف کنید»)، آن را ذکر کند.
- زبان راهنما **فارسی، ساده و کاربردی** باشد — نه توضیح فنی برنامه‌نویسی.
- این قانون برای همه‌ی تغییرات آینده هم معتبر است؛ کمک‌نکردن معادل باگ محسوب می‌شود.

⚠️ استثنا: اگر ویژگی جدید یک زیرمجموعه‌ی منطقی از یک بخش موجود است، می‌توان آن را در همان گره‌ی قبلی اضافه کرد (نیازی به گره‌ی جدید نیست) — ولی توضیحش نباید حذف شود.

## قانون ۸ — ارتباط و شفافیت

- اگر یک باگ کشف شد که نتیجه‌ی اشتباه قبلی Claude بود (نه کاربر)، این را به‌وضوح و بدون بهانه‌تراشی بگو، علت دقیق فنی را (نه فقط «یک مشکل بود») توضیح بده، و فوراً راه‌حل عملی (مثلاً دستور console برای رفع فوری) بده — قبل از توضیح طولانی.
- وقتی کاربر می‌گوید رفتارش عجیب بوده (مثل مصرف توکن غیرمنتظره)، اول با خیال راحت توضیح بده که چه اتفاقی افتاده و چرا نگران‌کننده نیست، بعد ادامه‌ی کار.
- هرگز فرض نکن یک مقدار «مثالی» که در توضیح زده شده (مثل یک تاریخ نمونه) همان مقدار واقعی مورد نیاز است — همیشه مقدار واقعی را با ابزار بررسی کن.

## قانون ۹ — همگام‌سازی لانچر `.bat` با آخرین نسخه (اجباری)

هر بار که نسخهٔ جدید HTML ساخته/تحویل می‌شود، **باید** لانچر ویندوز هم با همان نسخه یکسان شود — کاربر نباید جداگانه یادآوری کند:

1. `Sirman_Final.html` و در صورت وجود `Laegh_Final.html` را با محتوای آخرین نسخهٔ شماره‌دار همگام کن.
2. در `Sirman_Start.bat` و `OPEN_SIRMAN.bat` و `sirman_run.ps1` مقدار `SIRMAN_VERSION` / `$SirmanVersion` را دقیقاً به همان شمارهٔ نسخهٔ HTML (مثلاً `1405.5.18α`) به‌روز کن.
3. عنوان پنجرهٔ BAT و پیام‌های لانچر باید همان نسخه را نشان دهند.
4. فایل‌های فارسی `اجرای سیرمان.bat` / `اجرای لایق.bat` اگر فقط `Sirman_Start.bat` را صدا می‌زنند، کافی است Start همگام باشد؛ اگر محتوای مستقل دارند، آن‌ها هم باید نسخهٔ جدید را باز کنند.
5. تحویل بدون به‌روز کردن BAT/PS1 **ناقص** محسوب می‌شود.

## قانون ۱۱ — مرکز آپدیت (از ۱۴۰۵.۵.۱۸ε به بعد)

از نسخهٔ `1405.5.18ε` نرم‌افزار تب **تنظیمات → ⬆️ آپدیت** دارد. برای تغییرات بعدی:

1. **ترجیح اول:** به‌جای تحویل دوبارهٔ کل HTML، یک فایل کوچک `updates/Sirman_Update_*.json` با `magic: "SIRMAN_UPDATE"` بساز و بده.
2. فایل آپدیت می‌تواند نسخه، CSS، JS، و changelog را اعمال کند؛ برای تغییرات ساختاری خیلی بزرگ از پچ `replaceAppFile` (HTML کامل) استفاده کن.
3. **استثنا:** اگر خودِ هستهٔ آپدیت/لانچر/تست‌ها باید عوض شود، یا کاربر هنوز روی نسخهٔ قبل از ε است، یک HTML کامل نسخه‌دار تحویل بده.
4. نمونه و توضیح فرمت: پوشهٔ `updates/`.

## قانون ۱۲ — معماری بلندمدت (Modular Monolith)

منبع کامل: `docs/ARCHITECTURE_RULES.md`. خلاصهٔ اجرایی برای هر تغییر:

### اصل
قابلیت جدید نباید قابلیت قبلی را خراب کند. اولویت تصمیم: ۱) حفظ اطلاعات ۲) پایداری ۳) امنیت ۴) سازگاری نسخه ۵) نگهداری ۶) عملکرد ۷) امکانات جدید ۸) زیبایی UI.

### لایه‌ها
`HTML/JS (فقط UI)` → `Application Services` → `Business Logic` → `Data Access` → `Database`

- HTML مسئول UI است، نه Business Logic / Database / Backup پیچیده.
- هستهٔ هدف: .NET. پوستهٔ موجود WebView2 است.
- مسیر مجاز UI↔Core تا اطلاع ثانوی: Host Object به نام `sirmanHost` در `desktop/Sirman.Desktop/SirmanHostObject.cs` (از JS: `chrome.webview.hostObjects.sync.sirmanHost`).
- `fetch` به localhost، XHR، یا Blazor برای منطق کسب‌وکار ممنوع است مگر همین سند معماری با تصمیم صریح عوض شود.
- هر متد جدید Core باید به لیست مجاز `sirmanHost` اضافه شود، نه با مسیر موازی.
- مخفی کردن دکمه در UI به‌تنهایی امنیت نیست؛ Core باید دسترسی و اعتبار داده را مستقل بررسی کند.
- انبارها از Inventory Core مشترک؛ چاپ از Print Engine مرکزی؛ بک‌آپ مستقل از UI با Schema Version + Manifest + Checksum + Restore ایمن (Verify → موقت → Migration → Validation → Atomic Replace / Rollback).
- هر تغییر ساختار داده باید Migration نسخه‌دار داشته باشد. Migration قدیمی حذف نشود.
- سیستم موازی برای قابلیت موجود نساز. کد تکراری، Query پراکنده، و Hard-code مسیر/تنظیمات ممنوع است.

### انتقال تدریجی (وضعیت واقعی امروز)
بیشتر منطق هنوز داخل HTML است. این میراث است، نه الگوی ادامه.
- بازنویسی یک‌شبه یا حذف HTML ممنوع است.
- اگر قابلیت مشابه در HTML وجود دارد، همان را توسعه بده مگر تغییر شامل منطق کسب‌وکار مهم / داده / بک‌آپ / دسترسی باشد — در آن صورت متد Host Object در .NET بساز و UI فقط صدا بزند.
- مسیر باز کردن مستقیم HTML تا اطلاع ثانوی باید کار کند.

### چک‌لیست قبل از کد (بخش ۲۷ معماری)
1. این تغییر در کدام Layer است؟
2. آیا قابلیت مشابه قبلاً وجود دارد؟
3. آیا Business Logic از UI جدا می‌ماند؟
4. آیا Database Migration لازم دارد؟
5. آیا Backup/Restore همچنان کار می‌کند؟
6. آیا قابلیت‌های قبلی حفظ می‌شوند؟
7. آیا در نسخه‌های آینده قابل توسعه است؟
8. آیا از مسیر مجاز `sirmanHost` عبور می‌کند؟

اگر یکی منفی است، قبل از پیاده‌سازی ساختار را اصلاح کن.

## قانون ۱۳ — حاکمیت توسعه و حفاظت کد پایدار (دائمی)

منبع کامل: `docs/DEVELOPMENT_GOVERNANCE.md`. Baseline: `docs/STABLE_BASELINE.md`. رگرسیون: `docs/REGRESSION_SUITE.md`.
دروازهٔ تغییر فاز ۳ (اجباری، قبل از هر ویرایش منبع): `docs/PHASE_3_CHANGE_GATE.md`.

- کد پایدار محافظت می‌شود. الگو: ANALYZE → ISOLATE → MODIFY → TEST → REGRESSION → VERIFY → APPROVE.
- در فاز ۳ قبل از هر ویرایش منبع، `docs/PHASE_3_CHANGE_GATE.md` را اجرا کن. بدون `Gate: PASS` فایل عوض نکن.
- Feature جدید را مستقیم روی `main` ننویس. شاخه جدا، تست، رگرسیون، بعد merge.
- ماژول LOCKED (هویت فاکتور، برگشت انبار/حساب، گارانتی پایدار) را بدون باگ ثابت یا Requirement جدید عوض نکن.
- NO TEST = NO MERGE. PASS شدن تست به‌تنهایی VERIFIED نیست.
- چاپ کاغذ / restore واقعی / EXE ویندوز را با تست لینوکس FIXED اعلام نکن. اگر محیط نیست: BLOCKED یا NEEDS HUMAN VERIFICATION.
- وضعیت نهایی فقط یکی: COMPLETED / VERIFIED / BLOCKED / FAILED / NEEDS HUMAN VERIFICATION.
- بعد از هر کار، ۱۵ بند گزارش کار در سند حاکمیت را پر کن. CHANGELOG را برای انتشار به‌روز کن.

## قانون ۱۰ — در پایان هر کار، فایل را خودت بده (اجباری)
