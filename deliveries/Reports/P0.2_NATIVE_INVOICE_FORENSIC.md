### FIRST DIVERGENCE

**JS call site:** Test Page uses `pcDoNativeTestPage` + `printEngineBuildTestPageModel`. Invoice uses `printInv` **or** `pcDoPrint` + `printEngineBuildInvoiceModel`. Both then call the same `printEnginePrintNative`.

**Host parse:** Test Page parse has no seller/lines check. Invoice parse **can** fail before `Print()`. A parse miss returns `NO_DOCUMENT` and never calls `Print()`. Silent paperless `PRINT_SUBMITTED` is **not** that branch.

**C# renderer (first remaining split after a successful parse):**

After shared `NativeWindowsPrintService.Submit` setup (printer name, P0.1 `ApplyPaperSize`, landscape, margins):

```csharp
if (request.Kind == NativePrintRequest.KindTestPage)
    e.HasMorePages = false;
else
    e.HasMorePages = DrawInvoicePage(g, bounds, request.Invoice!, spec, page, ref lineIndex, logo);
if (request.Kind == NativePrintRequest.KindTestPage)
    DrawTestPage(...);
```

That `PrintPage` kind branch is the **first behavioral split** that can produce Test Page paper and Invoice no-paper on the **same** printer after P0.1.

P0.1 `ApplyPaperSize` is **shared**. Test Page physical PASS on this checkpoint **rules out** “A4 custom form never ejects” as an invoice-only cause.

### 2. Is `InvoicePrintModel` created?

**SOURCE — JS:** `printEngineBuildInvoiceModel` always returns a non-null object (`kind:'invoice'`, `engine:'native'`, `seller`, `items`/`lines`, logo, paper split).

**SOURCE — host:** `TryParseInvoice` constructs `InvoicePrintModel` only after non-empty `seller` and ≥1 line. Unit test `Invoice_ParseFromGetDataShape` parses the live `getData()` shape (`seller` + `items`) successfully on this tree.

**SOURCE JS:** not null. `printEnginePrintNative` returns `NO_DOCUMENT` only if `!model`, which the builder does not produce.

**SOURCE host:** `request.Invoice` is non-null whenever kind is `invoice` and parse succeeded. `request.Invoice!` in `PrintPage` is not reachable as null after a successful invoice `TryParse`. Invalid = missing seller or zero lines → parse false, `Print()` not called.

**SOURCE:** JS copies `seller` and mapped `items`/`lines` from `getData()` or last `invoices[]`. Host requires the same two fields. Other fields (phone, date, totals, font, margin) have defaults. Logo may be empty, `disk://…`, or a data URL; empty/bad logo becomes `TryLogo` → null (no throw).

### 9. Does `PrintPage` throw?

**NOT OBSERVED.** No exception type or message was captured.

`SafeFont` catches font construction. `TryLogo` catches decode.

**NOT OBSERVED.** If one occurred inside `Print()`, the host stores it on the job as `NATIVE_PRINT_FAILED` + type/message. That job JSON was not provided.

### 11. Does the renderer return before drawing?

**SOURCE — Test Page:** `DrawTestPage` always draws title + lines; no early return.

**SOURCE — Invoice:** `DrawInvoicePage` always draws header (brand, meta, rule, table header) once entered. Logo is skipped when null. There is **no** `return` before header drawing. Footer/totals are skipped only when `more==true` (pagination), after at least the header.

### 12. Does pagination produce zero pages?

**SOURCE: no**, if `Print()` runs. `PrintDocument` fires `PrintPage` ≥1 time. Empty `lines` cannot reach `Submit` (`TryParseInvoice` rejects). `NativePrintLayout.PageCount` is **not** used by `DrawInvoicePage`; live pagination is `y + rowH + 48 > bounds.Bottom`.

**SOURCE risk (invoice-only, not proven at shop):** if `MarginBounds` is too short to fit header + one row + 48 hundredths, `lineIndex` never advances and `HasMorePages` stays true → `Print()` may **not return** (no `PRINT_SUBMITTED`). Test Page forces `HasMorePages=false`. Default A4/A5 printable height in `NativePrintLayout` is far above that threshold; a degenerate `MarginBounds` from the driver is **NOT OBSERVED**.

### 13. Are any coordinates / measurements invalid?

**SOURCE:** both use `e.MarginBounds`. Table weights sum to 1.0. `Cols` snaps the last edge to `left+width`. Cell width is `Math.Max(4, …)`. Margins are `max(20, mm→hundredths)` from invoice `Margin` (default `8mm`) or test `spec.MarginMm` (8). No division by zero. Invalid canvas is **not** indicated in source for default A4/A5.

### 14. Are logo / image resources involved?

**SOURCE: invoice yes, test page no.**

- JS puts `logoSrc` / `logo` on the invoice model (global `logoSrc` or `d.logo`).

Logo is an invoice-only difference. Decode failure does **not** skip the rest of the page.

### 16. Are RTL / Persian operations involved?

**SOURCE: both paths** use `RtlFormat()` / `StringFormatFlags.DirectionRightToLeft`. Test Page draws Persian title + mixed `۱۲۳۴۵۶789`. Invoice adds Persian header, 16-col Persian headers, and `fa-IR` numeric formatting. RTL itself is **not** invoice-only. `fa-IR` culture **is** invoice-only.

### 17. Is the invoice canvas / page size invalid?

**SOURCE:** `ApplyPaperSize` is shared (P0.1). Paper token at the host comes from `printEnginePrintNative` split of `job.paper || model.paper || 'A4'`. Print Center default profile `a4-office` is `paper:'A4'`, `orientation:'portrait'`. Invoice builder default token is `'A4 landscape'` when paper is omitted, but **`job.paper` usually wins**, so the Print Center dropdown commonly overwrites the invoice landscape default. Test Page model `landscape` boolean is likewise ignored when `job.paper` is set.

If both jobs were printed from Print Center with the same `#pc-paper` value, host paper/form can be **identical**. Then canvas size is not the first divergence.

Invoice-only landscape surviving to the host is possible if the paper **string** contains `landscape`. `printEngineJob` defaults paper to `A4`, so this is uncommon. **NOT OBSERVED** for the failing click.

**NOT OBSERVED.** Host never reads a Win32 job ID after `Print()`. `PRINT_SUBMITTED` means `Print()` returned without throw — GDI accepted the job into the print controller, **not** that paper left the device. Test Page PASS shows this printer’s spooler **can** complete a native GDI job.

### 19. What happens to the spool job?

**NOT OBSERVED.** No Job ID, no queue dump, no driver error. Possible unproven outcomes if `Print()` returned: driver drop of a heavier GDI page; held/error job; device abort. Possible unproven outcomes if `Print()` did not return: hung `HasMorePages`, or throw → `NATIVE_PRINT_FAILED`.

## Paper / orientation note (not first invoice-only cause)

`printEnginePrintNative` prefers `job.paper` from `printEngineJob` / Print Center UI. `model.landscape` is applied only when **both** `opt.paper` and `job.paper` are empty. `job.orientation` is **not** copied into the native payload unless the paper string itself contains `landscape`.

This affects Test Page and Invoice the same way when both go through Print Center. It does **not** explain Test PASS / Invoice FAIL by itself.

## What `PRINT_SUBMITTED` means here

Set in `NativeWindowsPrintService.Submit` **after** `doc.Print()` returns. `Submit` has no catch around `Print()`. Exceptions during `Print()` / `PrintPage` skip this status and become `NATIVE_PRINT_FAILED` in `RunNative`.

Therefore:

- If the shop invoice UI ended in **queued / submitted success**: `Print()` returned; `PrintPage` did **not** throw; remaining gap is **after GDI submit** (spool/driver). Invoice-specific GDI payload is the only invoice-only difference left.
- If the shop invoice UI ended in **error**: `Print()` was not reached, or `PrintPage`/`Print()` threw. Need `errorCode` / `ErrorDetail`. **Not supplied.**

Do not treat submitted status as paper. Test Page is the paper proof for the shared path.
