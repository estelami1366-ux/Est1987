## 5. Sheet 180° vs glyphs-only — geometry

Postal paint order (`DrawPostalLabel` 277–286):

```text
gap = 10
colW = (bounds.Width - gap) / 2
rowH = (bounds.Height - gap) / 2

[ Sender   | Recipient ]   ← row 0  (logo on sender, left)
[ Sender   | Recipient ]   ← row 1  (duplicate)
```

A **2×2 grid of equal cards is invariant under 180° rotation of the whole sheet** as a *set of boxes*: the observer still sees four similar rectangles filling A5. That matches shop language: **cards PASS**, **text FAIL**.

Under a true 180° page mapping:

```text
Before:                After 180° of the whole sheet:
[ S ] [ R ]            [ R ] [ S ]
[ S ] [ R ]            [ R ] [ S ]
```

Logo (drawn only on sender cards, **left** column) would move to the **right** column. Latin `BrandEn` under the logo and `DrawImage(logo)` use the **same** `Graphics` object as `DrawString` — there is **no** text-only transform in source.

| Object | Same Graphics? | Separate transform? |
|---|---|---|
| Card borders (`DrawPath`) | yes | no |
| Logo (`DrawImage`) | yes | no |
| BrandEn `DrawString` (centered, **no** RTL flag) | yes | no |
| Address/name `DrawString` (RTL wrap) | yes | no |
| Zip/phone `DrawString` (LTR wrap + U+202A…U+202C) | yes | no |
| Fragile badge rect + `DrawString` | yes | no |

**Therefore:** if the shop sheet has **upright boxes + inverted text but an upright logo still on the left**, source cannot explain a text-only 180° (class D) — that would require a GDI/driver text pipeline not present in this repo. If **logo and Latin BrandEn are also inverted**, or **logo is on the right**, the failure is **whole-sheet 180°** (class A/B/C), and “cards PASS” is expected from 2×2 symmetry.

This agent has **no shop photograph**. Discriminator for review: **is the logo still on the left cards?**

## 6. StringFormat flags — can they rotate 180°?

Postal:

```csharp
PostalRtlWrapFormat:  new(StringFormatFlags.DirectionRightToLeft)
  Alignment = Near, LineAlignment = Near, Trimming = None
PostalLtrWrapFormat:  new()  // no DirectionRightToLeft
  Alignment = Near, LineAlignment = Near, Trimming = None
```

Test Page:

```csharp
RtlFormat: new(StringFormatFlags.DirectionRightToLeft | StringFormatFlags.LineLimit)
  Alignment = Near, LineAlignment = Center, Trimming = EllipsisCharacter
```

| Flag | Documented GDI+ effect | 180° rotation? |
|---|---|---|
| `DirectionRightToLeft` | horizontal RTL reading order; `Near` is the right edge | **No** — not an in-plane 180°. Test Page uses this flag and prints **upright**. |
| `DirectionVertical` | vertical (≈90°) | **Not used** |
| `NoWrap` | single line | **Not used** on postal wrap formats |
| `LineLimit` | do not wrap a line that would be clipped | Test Page only; not a rotation |
| `Alignment` / `LineAlignment` | box-relative alignment | placement, not glyph inversion |
| `Trimming` None vs EllipsisCharacter | clip vs `…` | P0.5R2 wrap fix; not orientation |

`DirectionRightToLeft` can **reorder** or, in some historical GDI+ reports, **mirror** along X when combined with a negative scale. This code never sets a negative scale. Mirroring is **not** the same as 180° (glyphs standing on their heads). Shop described **upside-down / ~180°**.

**Verdict:** StringFormat flags in this codebase **do not prove** 180° glyph rotation. Test Page is the control: same `DrawString` + RTL flag, upright output.

Unicode `NativePrintBidi.AsLeftToRight` (`U+202A` … `U+202C`) wraps zip/phone only. Embeddings change bidi order; they **do not** rotate glyphs 180°.

## 8. Printer driver orientation

Same printer prints Test Page upright. A driver-only 180° would still need a **job difference** (A5 vs A4 form, tray, DEVMODE landscape, “rotate 180 for envelopes”, manual-feed direction).

This repo never writes DEVMODE orientation bits beyond:

- `DefaultPageSettings.Landscape`
- `DefaultPageSettings.PaperSize` (installed A5 or constructed `SIRMAN-A5`)

**Do not blame the driver in isolation.** It remains a **plausible second stage** if the A5 form’s HDC mapping differs from A4 (double 90° = 180°, or tray feed 180°). That is **not proven** without `PRINT_SETTINGS_CREATED`, `PageBounds`, `Transform.Elements`, or a photo of logo left/right.

`Landscape = true` alone is specified to swap page axes (~90° relative to portrait paper), **not** 180°. A **second** 90° (driver + GDI both rotating) **can** yield 180°. Default postal source path sets `Landscape = false`, which **weakens** that specific double-rotate story **unless** the shop job was landscape or the installed A5 `PaperSize` is already swapped.

## 10. Classification (A–F)

| Class | Meaning | Finding |
|---|---|---|
| **A** | Graphics / page transform in app code | **Rejected for authored code** (no Rotate/Scale/Translate/Matrix/Save). Residual: **unknown print-controller/HDC transform** at runtime (not measured). |
| **B** | `PageSettings` / orientation | **First code-side orientation lever.** Default postal `Landscape=false`. Difference vs Test Page is **A5 vs A4 PaperSize**, not the Landscape bit, **unless** the shop postal job was landscape. `DrawPostalLabel` ignores Landscape and paints into `MarginBounds` whatever GDI supplies. |
| **C** | Printer driver orientation | **Not proven.** Possible only as **A5-specific** DEVMODE/tray interaction. Same driver prints Test Page correctly. |
| **D** | Text-only rendering config | **Rejected as sufficient cause.** Test Page uses RTL `DrawString` upright. No StringFormat flag is a 180° rotate. LTR zip/tel and logo share the same `Graphics`. |
| **E** | Different binary/runtime | **Rejected.** One `Submit` method; shop P0.5R2 kit is the given postal binary. |
| **F** | Other, with evidence | **Best fit for the physical description:** whole-sheet ~180° mapping **hidden by 2×2 rotational symmetry**, produced by the A5 page device (B and/or C), not by postal `DrawString`. |

### Most likely cause

**F, driven by B (A5 `PaperSize` / `MarginBounds` device mapping) possibly combined with C, not by postal text APIs.**

The app never rotates the postal `Graphics` object. Shop “cards OK + text upside-down” is the expected **visual** of a **180° sheet** on a symmetric 2×2 layout. The working Test Page is a **non-symmetric** A4 list, so the same 180° would have been obvious there — implying the inversion is **A5-job-specific** (form, bounds, feed), not a shared `DrawString` bug.

**Confidence**

| Claim | Confidence |
|---|---|
| App code does not apply 180° transform | **High** (source exhaustive) |
| StringFormat / font / bidi do not explain 180° | **High** (framework + Test Page control) |

## Minimal future fix recommendation (DO NOT IMPLEMENT IN THIS PACKET)

Do not guess `RotateTransform(180)` on postal without measuring the HDC.

1. **Shop discriminator (no code):** photograph one A5 postal sheet. Record: logo left vs right; whether Latin `BrandEn` is inverted; whether zip digits are inverted. Repeat Native Test Page **on the same A5 tray/feed** (Print Center paper A5) — if Test Page on A5 is also inverted, the defect is paper-device, not `DrawPostalLabel`.
2. **Instrumentation (future authorized packet):** in `PrintPage` only, log `e.PageSettings.Landscape`, `e.PageBounds`, `e.MarginBounds`, `PrintableArea`, `g.PageUnit`, `g.PageScale`, `g.Transform.Elements`. Compare Test Page vs Postal on the same printer. Optional: draw a non-symmetric marker (one filled corner) so 180° cannot hide.
3. **If logs show identity transform + Landscape=false + inverted logo:** treat as driver/tray (C); do not change postal layout.
4. **If logs show a 180° matrix or Landscape true with swapped bounds the UI did not request:** fix **paper contract / `DefaultPageSettings`** (P0.1 / P0.5R), not `DrawString`.
5. **Do not** “fix” RTL StringFormat, Tahoma, or P0.5R2 wrap for this symptom. **Do not** change Invoice, Test Page, HTML postal, Storage, or version in a speculative patch.
