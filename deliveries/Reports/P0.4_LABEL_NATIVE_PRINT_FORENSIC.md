Guess-id caveat (PROVEN in source, runtime UNKNOWN): card HTML uses «فرستنده» / «گیرنده» / «کدپستی» but `printEngineGuessDocId` keys on «پستی|برچسب». The postal HTML also has `@page{size:${pp.paper||'A4'}}` (settings default **A5**). Two `@page` rules; which wins in WebView2 is **UNKNOWN** at runtime. Source conflict: **PROVEN**.

## Label features

Current renderer: `updatePostalPreview` + `printPostal` CSS. No barcode library. No QR image. No tracking field on the card. Sender **name** is collected (`#snd-name`) but the printed card shows **address** as «فرستنده», not the name.

| Feature | Current implementation | Native feasibility | Risk |
|---|---|---|---|
| Persian/RTL text | `html dir="rtl"`, `body{direction:rtl}`, `.postal-wrap{direction:rtl}` | Existing `RtlFormat()` GDI | MEDIUM — GDI is not CSS |
| mixed numeric/Latin | zip/phone interpolated into RTL HTML with **no** `dir=ltr` / bidi isolate | `RtlFormat` + `fa-IR` already used on invoice amounts | **HIGH** for hyphenated digits (see Human issue H4) |
| barcode | **absent** on postal cards | no barcode encoder in Desktop | N/A today; HIGH if required later |
| QR | **absent** on postal cards (`PRINT_TEMPLATE_DEFAULT.qr` is Print Center wrap-only; `skipWrap` skips it) | no QR encoder | N/A today |
| logo | `<img src=logoSrc>` float left in sender card | `TryLogo` already on invoice | MEDIUM placement |
| sender information | addr, zip, tel, person; name stored but not on card | new model fields | LOW |
| recipient information | addr, zip, tel, name, note | new model fields | LOW |
| date | history only (`recordPostalHistory`); **not** on printed card | optional | LOW |
| postal code | `#snd-zip` / `#rcv-zip` as text | string field | **HIGH bidi** if value like `2000-35155` |
| tracking/reference | **absent** | not required | N/A |
| custom paper size | settings A5/A4; Print Center may inject A4 `@page` | `ParsePaper` A4/A5 ISO + `label` 100×150mm | MEDIUM (two sources today) |
| multiple labels | hardcoded 4 cards; `ps.postal.count` unused | would need to honor count | MEDIUM (config already lies) |
| copies | Print Center `job.copies` via HTML enqueue | `PrinterSettings.Copies` | LOW |
| cut/offset/margin | `@page` margin 10mm; boxes padding 10px 12px | `ParseMarginMm` | MEDIUM |
| images | logo + optional `bgImage` watermark (`printBgCss`) | logo yes; CSS `body::before` watermark **no** native equivalent | HIGH for bg watermark |
| CSS positioning | flex two-column, float logo, fragile badge | GDI rectangles, not flex | **HIGH** pixel match |
| font dependencies | Tahoma | `SafeFont("Tahoma")` | LOW |

Do not assume native C# reproduces HTML/CSS pixel-for-pixel. **PROVEN:** it cannot be claimed from source.

## RTL / bidirectional (H4)

Known human example: stored `2000-35155` seen as `35155-2000`.

Postal zip/phone:

```text
stored value:    input #snd-zip / #rcv-zip / tel as typed (no sanitizer)
displayed value: same string inside RTL .postal-box (preview)
printed value:   same string inside RTL print HTML (direction:rtl)
```

Unlike some account fields (`dir="ltr"` on `#sale-acc-ref`), postal zip inputs have **no** LTR isolate. Preview and print both inherit page RTL.

**Postal Label CAN be affected** by the same bidi class as H4. This round does **not** prove the shop printed `2000-35155` on a label. Source allows the reversal. Do not fix here.

Native `StringFormatFlags.DirectionRightToLeft` has the same class of hyphen+digit issue. Migration does not automatically fix H4.

## Native feasibility (do not implement)

Packet questions:

1. Represent as native print request? **Yes**, as a **new** kind. Current `TryParse` rejects it.
2. New `kind`? **Yes** (e.g. `postal` / `postalLabel`). `IsNativePaper` and Host `nativePaper` currently allow only `testPage`/`invoice`.
3. New model? **Yes** (sender, recipient, zips, phones, note/fragile, logo, border, count, paper).
4. Existing paper/layout? **Partially.** A5/A4 ISO forms exist (P0.1). Token `label` is 100×150mm for Zebra profile, not the postal A5 sheet of two-up cards.
5. Print without WebView2? **Yes**, after a GDI renderer exists. Not today.
6. Barcode/QR? **Not on current postal print.** Adding later needs a library native does not have.
7. RTL text? **Partially** via existing `RtlFormat`. Hyphenated numbers remain a risk.
8. Exact label dimensions? **Not guaranteed.** CSS flex + dual `@page` vs ISO A5 form.
9. Margins/offsets? **Mappable**, not identical (10mm vs layout 8mm default).
10. Existing user-facing config? **Should be honored** (`ps.postal.*` + Print Center printer). Today count/logo flags are already incomplete in HTML.

```text
New model needed:                 YES
New kind needed:                  YES
New renderer needed:              YES (DrawPostalLabel or equivalent)
Existing infrastructure reusable: Host EnqueueNative, ResolvePrinter,
                                  NativePrintLayout A4/A5, TryLogo, RtlFormat
WebView2 required:                NO for a future native paper path
                                  YES for today's physical path
```

`IPrintService` already describes HTML enqueue as “اسناد کاغذ هنوز مهاجرت‌نشده”. Postal is that class.

## Decision

```text
OPTION B — MIGRATE POSTAL LABEL TO NATIVE C#
```

Not A: routing **is** HTML/WebView2; that is the divergence from the working native paper engine. Failure is not proven unrelated to that nature.

Not C as the long-term physical design: two physical backends (WebView2 + GDI) is the present accident. Preview may stay HTML; **paper** should not stay WebView2.

B is **not** chosen because HTML is old. It is chosen because:

- source proves physical postal print is HTML → WebView2;
- native paper already exists and physically PASSed on Native Test;
- IPrintService already splits unmigrated HTML paper vs native;
- postal features without barcode/QR are a finite GDI layout (cards, logo, text, optional fragile);
- existing postal UI/settings can remain the operator surface.

**Not implemented.** Pixel-perfect CSS is **not** promised. H4 bidi is **not** fixed by this decision.

### If B is later authorized (safety — packet §11)

```text
Existing Postal Label HTML renderer
        ↓

        ↓

        ↓

        ↓
human verification on shop printer
        ↓
parity check (fields, paper, copies, fragile/border)
        ↓

```

No destructive removal of HTML on first migration. Do not touch Native Test Page or native invoice in that future change unless a later packet says so.
